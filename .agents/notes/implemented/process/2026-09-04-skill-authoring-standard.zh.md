# Agent Note: Skill 编写标准

Status: implemented

## 问题

没有统一的编写标准时，Skill 容易变成范围宽泛、叙事性很强的提示词：元数据不足以匹配任务，正文又把执行选择留给
agent 猜测。这会增加提示词开销，鼓励创建重复 Skill，也让失败难以验证或交还给用户。

## 决策

Skill 编写将两种契约分开：简短元数据负责匹配任务，正文负责指导匹配后的 agent 执行。[prose-standard](../../../skills/prose-standard/SKILL.md)
负责清晰表达和删除推理泄漏；本笔记补充 Skill 专属的路由与执行边界。

### 元数据是匹配契约

默认的项目级文件位置是 `.agents/skills/<skill-name>/SKILL.md`。其 YAML frontmatter 必须包含 `name` 与 `description`：

```yaml
---
name: api-debugging
description: Diagnose API failures in this repository, identify the owning package, and verify fixes with the smallest relevant checks.
---
```

- `name` 使用 kebab-case，并标识一个连贯的任务域。
- `description` 说明 Skill 处理什么任务以及何时适用，不写成口号，也不放入完整流程。
- 只有在额外的匹配条件能实质改善路由时，才增加可选的 `whenToUse`。
- 按预期的调用入口有意识地设置 `disable-model-invocation` 与 `user-invocable`。如果 Skill 还有产品专用的调用元数据，该元数据
  必须与 frontmatter 策略一致。

路由元数据应足够短，以便作为目录条目使用；不能为了省略正文而把执行细节塞进元数据。

### 正文是执行契约

匹配后，正文必须让另一个 agent 无需猜测关键步骤即可行动。正文应说明范围、前置条件、有序工作流、条件分支、失败处理、验证证据与限制。
可采用以下默认结构：

```markdown
# API Debugging

## Scope

## Preconditions

## Workflow

## Verification

## Limitations
```

正文用于记录规则和判断，不是概念文章。优先使用直接指令，例如“先读取当前注册的 Service 接口，再编写调用代码；不要根据 Service 名称猜测方法签名”。
要写清先检查什么、依据什么选择下一步、可以修改或调用哪些文件和工具、前置条件缺失时如何处理，以及何时停止并报告不确定性。写出最小相关检查和代表成功的可观察结果。

### 边界与渐进式披露

一个 Skill 应聚焦一个任务域。独立主题应拆成多个 Skill；如果必须放在一起，则在正文中明确属于范围内和范围外的情况。不要使用“处理所有开发任务”这类兜底描述。

目录视图只展示 `name` 与 `description`；Skill 匹配后才加载完整正文。因此，description 必须足以完成路由，正文不得重复 frontmatter；参考资料、脚本与资源应当只在工作流需要时引用和加载。
不要在路由表面枚举无关资源。

### 编写与评审规则

删除背景故事、重复规则、装饰性文字和过程旁白，但保留行为约束、所有权、时机、例外、失败后果与兼容性承诺。把调用元数据和可见诊断视为行为。
当所需的平台接口、命令、权限或输入无法确定时，Skill 必须说明如何报告缺口；禁止指导 agent 猜测。

## 验证

新建或实质修改的 Skill 满足以下条件后才算完成：

1. 只看 `name` 与 `description`，读者就能判断该 Skill 是否匹配当前任务。
2. 匹配后的 agent 可以执行工作流，不需要自行发明关键步骤、命令、接口或成功条件。
3. 每个有意义的分支都写明触发条件、动作、失败处理与停止条件。
4. Skill 写明限制和非目标，检查能够产生具体证据。
5. 正文不重复 frontmatter，不包含推理记录或无关资源目录。
6. 相关的 frontmatter 解析器、调用策略校验、文档门禁和任务专属检查均通过；只报告实际运行过的检查。

## 曾考虑的替代方案

**把完整流程放进 `description`。** 否决，因为路由元数据会变得昂贵、难以扫描，也难以与执行指令独立演进。

**提供一个宽泛的开发 Skill。** 否决，因为匹配不准确且无关分支会让 Skill 更难正确调用，并鼓励把本应拆分到多个 Skill 的条件性文字堆在一起。

**先写叙事性介绍，再写规则。** 否决，因为过程旁白和背景会延迟可执行契约，还可能暴露推理，却没有定义必须遵守的行为。

**在目录条目阶段加载所有参考资料、脚本和资源。** 否决，因为渐进式披露要求目录保持精简，并且只在匹配后的工作流需要时加载支撑材料。

## 后果

今后的 Skill 使用小而稳定的 frontmatter 作为路由表面，使用可执行且有边界的正文作为工作流。评审可以将匹配质量与流程完整性分开检查，失败报告也可以指向明确的缺失前置条件或验证结果。
新增 Skill 或修改调用策略仍属于流程变更：同步更新相关 Skill 元数据和 sidecar，运行适用门禁，并将产品专属运行时契约保留在其所属源码或决策记录中，避免在本笔记重复。
