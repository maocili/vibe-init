# Agent Note: Upgrade ownership migration

Status: implemented

## Problem

旧的 upgrade 复用 init 的冲突策略，无法区分初始化器拥有的内容和项目资产。因此编辑过的 skill 无法安全刷新，笔记被误判为过期副本，也无法说明旧文件是否可以删除；依赖安装还没有记录已应用的规则包版本。

## Decision

`upgrade` 现在通过项目级 `.vibe-init/state.json` 执行按所有权分类的迁移。marker 段、生成文档、声明的工具链文件、声明的 skill 文件和笔记骨架说明文件属于初始化器拥有的内容，可从当前规则包刷新。日期命名的 Agent Note、笔记清单、业务文档和未知文件属于项目资产并保留。只有状态清单证明归属且安装哈希未改变时才删除旧受管文件；已修改或无法判断的路径报告 conflict 并保留。每次写入前展示分类计划；非交互环境必须使用 `--yes`；工具链变化先安装依赖，全部成功后才原子写入状态。

初始化器只拥有 `.vibe-init/` 和 `vibe-init:*` 命名空间。旧的 `.dsh-vibe/` 命名空间和 `dsh-vibe:*` marker 不会被发现、迁移、修改或删除。所有权边界与[独立硬切 Note](../simplification/2026-09-06-standalone-vibe-init.zh.md)交叉链接；移除理由和已失去能力的记录仍以该 Note 为准。

## Alternatives considered

**复用 init 的冲突检测。** 这能维持旧的安全规则，却无法实现版本迁移，也无法区分受管依赖和用户新增内容。

**覆盖 `.agents/` 下的所有路径。** 实现简单，但会破坏 Agent Note、用户新增 skill 文件和初始化器不拥有的项目文档。

**仅按文件名推断旧文件归属。** 固定路径能帮助无状态项目迁移，但仅凭文件名删除可能误删无关文件；因此旧项目迁移只报告歧义，不删除未知路径。当前硬切完全不检查退役命名空间。

## Consequences

新项目和升级后的项目都会保存带 schema 版本的所有权快照，以及规则源和已安装内容的哈希。`status` 与 `audit` 会展示状态缺失、无效、过期、漂移和待安装依赖。规则包变更仍必须在同一变更中刷新 manifest 哈希，并同步需求、验收证据和当前行为文档。受管路径的所有权属于初始化器，日期命名笔记和用户内容的所有权属于项目。
